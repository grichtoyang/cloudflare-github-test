# 每日盤前分析 V1.0 — ANALYSIS_RULES.md

```text
文件名稱：ANALYSIS_RULES.md
文件版本：V1.0
文件狀態：內部規則修正版，待跨文件驗證
適用時區：Asia/Taipei
備註：本文件可提交至 GitHub；正式定案前仍須完成跨文件驗證
```

# 1. 文件目的與責任範圍

本文件定義「每日盤前分析 V1.0」的分析規則、資料有效性、Fallback、模組判定、整合邏輯、風險與最低交付要求。

本文件不負責：

- 報告的實際版面與欄位排列；由 `REPORT_TEMPLATE.md` 定義。
- Dashboard 的畫面與元件規格；由 `DASHBOARD_SPEC.md` 定義。
- 執行流程、排程、GitHub Actions、錯誤後續執行控制；由執行 Prompt／Runtime 定義。
- 即時下單或自動交易。

---

# 2. 分析模組

分析固定分為五個模組：

1. `spot`：台股現貨與現貨籌碼
2. `global_markets`：美股、半導體、利率、美元、匯率、亞洲市場、BTC、重要新聞
3. `futures`：台指期價格、成交量、未平倉量、三大法人部位、現貨／期貨關係
4. `options`：選擇權籌碼、到期結構、關鍵位
5. `summary`：跨模組整合、方向、情境、關鍵支撐壓力與風險

`summary` 不得自行創造未出現在前四個模組中的原始資料。

---

# 3. 資料分層規則

所有資料必須區分為以下層級：

## 3.1 原始資料

來源直接提供、未經模型計算的數值或文字。

標記：

```text
data_type = raw
```

## 3.2 Proxy／轉送資料

由官方資料經已驗證的 Proxy 取得，內容仍屬來源資料。

標記：

```text
data_type = proxy_raw
```

## 3.3 Fallback 資料

主要來源失敗後，由備援來源取得的資料。

標記：

```text
data_type = fallback_raw
```

## 3.4 計算值

依已確認公式由原始資料計算而來，例如：

- 漲跌點
- 漲跌幅
- OI 變化
- 現貨／期貨價差
- Max Pain
- Gamma Wall
- Gamma Flip
- 距離現價

標記：

```text
data_type = calculated
```

## 3.5 推導值

由多項資料經規則推導而來，例如：

- 方向
- 信心
- 支撐／壓力分級
- 多空一致性
- 交易情境

標記：

```text
data_type = derived
```

## 3.6 分析解讀

對事實與計算結果的文字說明。

標記：

```text
data_type = interpretation
```

不得將 `calculated`、`derived` 或 `interpretation` 誤標示為官方原始資料。

---

# 4. 日期、時間與資料有效性

1. 所有報告與資料時間一律使用 `Asia/Taipei`。
2. 必須區分：
   - `analysis_date`：本次分析日期
   - `market_date`：資料所屬交易日期
   - `data_timestamp`：資料取得或更新時間
   - `generated_at`：報告產出時間
3. 不得將取得日期直接當成市場資料日期。
4. 非交易日不得虛構市場收盤資料。
5. 美股、海外市場與台股可能有不同交易日，必須保留各自的 `market_date`。
6. 夜盤資料必須標明交易時段，不得與日盤資料無標示混合。
7. 若資料日期不明，該資料不得作為核心方向判定依據。

# 5. 狀態碼標準

## 5.1 來源狀態 `source_status`

只允許：

```text
success
failed
timeout
blocked
invalid
empty
not_available
```

## 5.2 資料品質 `data_quality_status`

只允許：

```text
complete
partial
stale
invalid
missing
```

說明：

- `complete`：必要欄位完整且有效。
- `partial`：部分欄位缺失，但仍可使用。
- `stale`：資料有效性受時間延遲影響。
- `invalid`：資料格式、數值或邏輯驗證失敗。
- `missing`：沒有可用資料。

## 5.3 Fallback 狀態 `fallback_status`

只允許：

```text
not_used
used
failed
```

`fallback` 不是資料品質狀態，不得與 `complete`、`partial` 等混用。

## 5.4 模組狀態 `module_status`

只允許：

```text
completed
completed_with_warnings
partial
insufficient_data
failed
```

## 5.5 報告狀態 `report_status`

只允許：

```text
completed
completed_with_warnings
partial
insufficient_data
failed
blocked_by_access
blocked_by_rule_conflict
```

規則：

- `completed`：所有核心模組完成，核心資料有效，無未解決核心錯誤。
- `completed_with_warnings`：核心分析完成，但存在非核心缺失、Fallback、延遲或警告。
- `partial`：部分核心模組完成，仍可產出有限分析。
- `insufficient_data`：核心資料不足，無法形成可靠方向判斷，但仍須產出報告。
- `failed`：流程或分析執行失敗，但仍須記錄錯誤並產出可產出的報告內容。
- `blocked_by_access`：主要與備援來源均因權限、網路或存取限制無法取得核心資料。
- `blocked_by_rule_conflict`：規則或資料定義存在未解決衝突，無法安全判定。

不得使用未列出的狀態碼，例如：

```text
failed_but_report_generated
fallback
success
unknown
```

若流程失敗但已產出報告，使用：

```text
report_status = failed
```

並在 `unfinished_items` 或錯誤紀錄中註明「報告已產出但流程未完整成功」。

# 6. 來源優先順序與 Fallback

## 6.1 一般來源優先順序

原則上依下列順序：

1. 官方 API
2. 已驗證的官方 Proxy
3. 官方備援 API／Proxy
4. 已驗證的主要金融資料來源
5. 已驗證的備援金融資料來源
6. 最近一次有效資料
7. `missing`

實際來源順序若由執行 Prompt 指定，須以執行 Prompt 的明確規則為準，但不得違反本文件的資料有效性規則。

## 6.2 Fallback 使用規則

使用 Fallback 時必須記錄：

- 原始來源
- 失敗原因
- 實際採用來源
- 資料日期
- 取得時間
- 是否延遲
- 對分析信心的影響

## 6.3 最近一次有效資料

最近一次有效資料只可在以下條件同時成立時使用：

1. 該資料集本身允許使用歷史值。
2. 資料日期明確。
3. 沒有更新中的重大事件會使舊資料失效。
4. 報告中明確標示為 `stale` 或 `fallback_raw`。
5. 不得將其當成當日最新資料。

以下資料原則上不得僅依最近一次有效資料判定當日即時方向：

- 台指期最新價格
- 夜盤最新價格
- 當日選擇權即時關鍵位
- 當日即時成交量
- 當日即時法人流量

## 6.4 Fallback 對信心的限制

- 使用主要官方來源且資料完整：可評估 `high`。
- 使用官方 Proxy：若內容與官方資料一致，可維持正常信心。
- 使用一般備援來源：最高通常為 `medium`。
- 使用最近一次有效資料：最高為 `low`。
- 核心資料缺失：不得標示 `high`。
- 核心資料不足以判斷方向：必須使用 `insufficient_data`。

# 7. 核心資料與最低交付規則

## 7.1 核心資料

核心資料包括：

- 台股現貨基本行情
- 台指期價格或可用的近月期貨資料
- 至少一組可驗證的市場外部環境資料
- 選擇權關鍵位或明確標示其缺失
- 必要的資料日期與來源狀態

## 7.2 最低交付要求

無論中間發生何種錯誤，執行流程均不得在未產出 Markdown 報告前停止。

即使資料取得失敗，也必須產出：

1. 已成功取得的資料
2. 已完成的模組
3. 失敗的資料源
4. Fallback 嘗試結果
5. 缺失資料
6. 未完成項目
7. 對分析能力的影響
8. 最終報告狀態

不得用空白、猜測值或自行補值掩蓋失敗。

# 8. 方向判定規則

方向不是單一指標的結果，必須依多項證據判定。

## 8.1 偏多

只有在以下條件大致成立時，才可判定偏多：

- 現貨、期貨或外部市場至少有兩項支持多方；
- 沒有同等強度的核心反向證據；
- 關鍵支撐未被有效破壞；
- 若選擇權資料有效，關鍵位沒有明顯否定多方的結構；
- 資料品質足以支撐判斷。

## 8.2 偏空

只有在以下條件大致成立時，才可判定偏空：

- 現貨、期貨或外部市場至少有兩項支持空方；
- 沒有同等強度的核心反向證據；
- 關鍵壓力未被有效突破；
- 若選擇權資料有效，關鍵位沒有明顯否定空方的結構；
- 資料品質足以支撐判斷。

## 8.3 震盪

以下情況可判定震盪：

- 多空證據接近；
- 現貨與期貨方向不一致；
- 價格位於主要支撐與壓力之間；
- 選擇權結構顯示價格可能受限於區間；
- 缺乏有效突破或跌破證據。

## 8.4 方向不明

以下情況判定方向不明：

- 核心模組彼此衝突；
- 關鍵資料日期不一致且無法校正；
- 價格、法人、選擇權訊號互相矛盾；
- 只有單一證據支持方向；
- Fallback 資料過多而無法確認現況。

## 8.5 觀望

`觀望` 是行動建議，不等同於市場方向。

例如：

- 市場方向偏多，但尚未突破確認，行動為觀望。
- 市場方向偏空，但尚未跌破確認，行動為觀望。
- 市場處於震盪區間，行動為觀望。

## 8.6 資料不足

若核心資料不足以支持任何方向，必須使用：

```text
direction = 資料不足
confidence = insufficient_data
```

不得以「推測」、「大概」或主觀印象填補。

# 9. 信心分級

## 9.1 High

需同時符合：

- 核心資料完整且有效；
- 至少兩個主要模組方向一致；
- 沒有未解決的重大衝突；
- 沒有關鍵資料使用過期值；
- 方向判定具有明確支持與失效條件。

## 9.2 Medium

符合下列任一情況：

- 主要證據大致一致，但存在部分缺失；
- 使用官方 Proxy 或有限 Fallback；
- 有輕度模組衝突，但不影響主要結論；
- 關鍵位或外部市場資料部分延遲。

## 9.3 Low

符合下列任一情況：

- 使用最近一次有效資料；
- 核心資料部分缺失；
- 模組之間有明顯衝突；
- 主要判斷依賴單一資料集；
- 關鍵位計算資料不完整。

## 9.4 Insufficient data

符合下列任一情況：

- 無法取得足夠核心資料；
- 核心資料無法驗證；
- 主要資料來源與備援來源均失敗；
- 規則衝突導致不能安全判定。

`high` 不得與 `stale`、`missing` 或重大 `invalid` 核心資料並存。

# 10. spot 規則

`spot` 必須分析：

- 加權指數
- 漲跌點與漲跌幅
- 成交量
- 三大法人買賣超
- 融資
- 融券
- 借券
- 融資維持率（若有）
- 前值與變化

分析必須分開呈現：

1. 原始事實
2. 與前值的變化
3. 量價結構
4. 法人籌碼結構
5. 可能影響
6. 資料限制

不得只因三大法人單日買超便直接判定大盤必然上漲。

# 12. futures 規則

必須區分：

- 近月契約
- 交易日期
- 日盤／夜盤

- 漲跌
- 成交量
- 未平倉量
- 現貨／期貨價差
- 三大法人淨部位
- 前值與變化

- OI 增減是否支持價格方向。

不得將現貨法人資料與期貨法人資料重複當成兩份獨立證據而過度放大結論。

- 不得在資料缺失時自行估算；
- 不得把關鍵位視為絕對支撐或壓力；
- 不得只依 Max Pain 判定方向。

# 14. Opening Range 與價格行為

## 14.1 Opening Range

Opening Range 固定定義為：

```text
08:45–09:15
1-minute bars
```

輸出：

- `OR_High`
- `OR_Low`
- OR 資料日期
- OR 資料完整性
- OR 狀態

## 14.2 OR 獨立性

Opening Range：

- 獨立於手動 Key Level／Zone；
- 不與其他 Zone 合併；
- 不受手動 Zone 最大 50 點寬度限制；
- 可作為當日最早遇到的關鍵區之一。

## 14.3 價格行為限制

盤前分析可以描述：

- 可能的突破位置；
- 可能的失敗位置；
- 需要觀察的確認條件；
- 真突破／假突破的風險。

但盤前報告不得把尚未發生的價格行為寫成已確認訊號。

即時交易系統中的：

- 真突破／假突破
- VSA
- 量價效率
- BOS
- 回踩確認
- ATR 停損

屬於後續交易引擎的執行邏輯，不得在盤前資料不足時預先宣告已成立。

# 15. Summary 整合規則

## 15.1 證據分層

整合時依序考慮：

1. 資料有效性
2. 現貨與期貨價格結構
3. 法人與 OI 結構
4. 選擇權關鍵位與到期結構
5. 全球市場外部環境
6. 風險與資料限制

## 15.2 不得簡單投票

不得使用：

```text
多方模組數量 > 空方模組數量 = 偏多
```

必須說明：

- 哪些證據支持方向；
- 哪些證據反向；
- 哪些資料重複；
- 哪些資料權重受限；
- 哪個條件會使結論失效。

## 15.3 模組衝突

- 現貨與期貨衝突：標示衝突，優先觀察價格與 OI 的一致性。
- 現貨與選擇權衝突：不得只依選擇權關鍵位否定價格行為。
- 全球市場與台股本地資料衝突：全球市場作為背景，不得單獨覆蓋本地價格結構。
- 核心資料嚴重衝突：方向降級為 `方向不明`，信心不得高於 `low`。

## 15.4 證據去重

以下不得重複計權：

- 同一來源的原始值與其直接計算值；
- 同一法人資料在不同模組的重複呈現；
- 同一新聞在多個來源的重複報導；
- 同一選擇權資料衍生出的多個相同結論。

---

# 16. 支撐、壓力與情境

支撐／壓力可來自：

- 前高／前低
- Opening Range High／Low
- 已驗證的選擇權關鍵位
- 已確認的價格結構
- 其他明確標示來源的關鍵價位

每個關鍵位必須標示：

- 價位
- 類型
- 來源
- 資料日期
- 距離現價
- 重要性
- 失效條件
- 是否使用 Fallback

支撐壓力不是保證價格反轉的位置。

---

# 17. 錯誤、缺失與衝突處理

任何錯誤都必須記錄：

- 發生模組
- 發生時間
- 資料來源
- 錯誤類型
- 錯誤訊息
- 是否重試
- 是否使用 Fallback
- 對分析的影響
- 未完成項目

若無法完成某一模組：

- 不得捏造該模組內容；
- 不得阻止其他模組繼續；
- 必須將該模組標示為 `partial`、`insufficient_data` 或 `failed`；
- 最終仍須產出 Markdown 報告。

---

# 18. 模組輸出最低欄位

每個模組至少應具備：

```text
module
module_status
market_date
data_timestamp
timezone
source
```

# 19. Dashboard 與報告的責任邊界

`ANALYSIS_RULES.md` 只規定：

- 分析結果必須可被結構化輸出；
- 每個數值要能追溯來源與日期；
- 每個模組要有狀態；
- 缺失與 Fallback 必須可被呈現；
- Dashboard 不得自行改寫分析結論。

以下內容不在本文件定義：

- Dashboard 的實際版面；
- 顏色；
- 元件排列；
- 圖表尺寸；
- 報告 Markdown 的具體欄位順序；
- UI 互動行為。

# 20. 最終狀態判定

依優先順序判定：

1. 若規則衝突未解決：`blocked_by_rule_conflict`
2. 若核心資料因存取限制無法取得：`blocked_by_access`
3. 若流程失敗但仍有部分結果：`failed` 或 `partial`
4. 若核心資料不足：`insufficient_data`
5. 若核心分析完成但有警告：`completed_with_warnings`
6. 若核心分析完整且有效：`completed`

不得因「已產出檔案」就直接標示 `completed`。

# 21. 禁止事項

禁止：

- 虛構不存在的數值；
- 用猜測值補齊缺失資料；
- 把舊資料當成最新資料；
- 把計算值當成官方原始值；
- 把推導結論當成事實；
- 只依單一指標判定方向；
- 只依單日法人買賣超判定趨勢；
- 只依 Max Pain 判定行情；
- 將選擇權關鍵位視為絕對支撐壓力；
- 把尚未發生的突破寫成已確認；
- 因單一來源失敗而提前停止整個流程；
- 未產出 Markdown 報告就停止；
- 讓 Dashboard 自行改寫分析結果；
- 在規則衝突未解決時強行給出高信心結論。
